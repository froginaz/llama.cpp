# INTEGRATION.ko.md - 배경 지식이 없는 독자를 위한 통합 가이드 해설 (한국어)

> 이 문서는 [INTEGRATION.md](INTEGRATION.md)(영문, 구현 에이전트용 규격)를
> 처음 읽는 사람도 이해할 수 있도록 배경부터 풀어 쓴 해설판이다. 규격의
> 원본은 영문판이며, 충돌 시 영문판이 우선한다.

## 0장. 이 코드가 풀려는 문제

**LLM이 답을 만드는 방식**부터 시작한다. 언어 모델은 문장을 토큰(단어 조각)
단위로 읽는데, 각 토큰을 처리할 때마다 "이 토큰에 대한 계산 결과(K와 V라는
두 벡터)"를 만들어 저장해 둔다. 이 저장소가 **KV 캐시**다. 저장하는 이유:
다음 토큰을 만들 때 **앞의 모든 토큰의 K/V를 다시 읽어야** 하기 때문이다.
저장해 두지 않으면 토큰 하나 만들 때마다 문장 전체를 재계산해야 한다.

실제 사용 상황을 보자. 에이전트 프레임워크(OpenClaw 등)는 매 대화 턴마다
이렇게 보낸다:

```
1턴: [시스템 프롬프트 3000토큰] + [도구 설명 5000토큰] + [질문 50토큰]
2턴: [시스템 프롬프트 3000토큰] + [도구 설명 5000토큰] + [질문 50토큰]
      + [1턴의 답변 200토큰] + [새 질문 40토큰]
```

**앞의 8,000토큰이 매번 똑같이 반복**된다. 매번 처음부터 계산하면 사용자는
새 질문 40토큰이 아니라 8,290토큰 전체의 계산 시간을 기다린다. 첫 글자가
나올 때까지의 시간을 **TTFT**(Time To First Token)라 하는데, 반복 구간을
계산에서 빼는 것 - 이것이 **prefix(접두사) 캐싱**이고 이 코드의 목적이다.

## 1장. 왜 우리 상황에서는 특별히 어려운가

일반 GPU라면 간단하다. KV 캐시가 host(CPU 쪽 프로그램)가 관리하는 메모리에
있으니 "앞 8,000토큰은 이미 있네, 재사용" 하면 끝이다.

우리의 NPU는 다르다. **KV 캐시가 NPU 내부 메모리에 있고, host는 그 내용을
읽을 수 없다**(host non-visible). 비유하면:

> 창고(NPU 메모리)에 물건(K/V)을 보관하는데, 관리인(host)은 창고에 들어갈
> 수 없다. 물건을 넣으라고 지시만 할 수 있고, 안에 뭐가 있는지 직접 확인은
> 불가능하다.

들여다볼 수 없는 창고를 관리하는 방법은 하나뿐이다 - **장부를 쓰는 것**.
"3번 선반에 A를 넣으라고 지시했고, 성공 보고를 받았다"를 꼼꼼히 기록하면
창고를 안 봐도 내용물을 안다. 이 코드의 두 모듈은 **두 가지 다른 위치에서
쓰는 두 종류의 장부**다.

## 2장. 두 개의 모듈 - 계획자와 관측자

소프트웨어 스택은 층으로 되어 있다:

```
[응용/서버]     <- 사용자의 프롬프트 "전체"를 아는 층
     |  프롬프트를 512토큰짜리 조각(ubatch)으로 잘라 내려보냄
     v
[ggml-backend]  <- 조각을 "하나씩" 받아 NPU에 실행시키는 층
     v
[NPU firmware]  <- 실제 계산, KV 창고 보유
```

- **KvLedger (모듈 1) = 계획자.** 위층에서 산다. 프롬프트 전체를 받아
  "앞 8,000토큰은 창고에 있으니 건너뛰고, 새 290토큰만 조각내 보내자"라는
  **계획**을 세운다.
- **BackendStreamTracker (모듈 2) = 관측자.** 아래층에서 산다. 계획은 세울
  수 없다 - 전체 프롬프트를 본 적이 없고 조각이 하나씩 흘러올 뿐이다. 대신
  흘러오는 조각을 보고 "이 조각은 지난번과 똑같다. 계산 생략!"이라고
  **판별**한다.

영문판 첫머리의 선택표는 이 말이다: **llama.cpp 본체를 못 고치는 상황이면
관측자(모듈 2)부터, 자기 프로그램을 처음부터 짜는 상황이면 계획자(모듈 1)
를** 쓰라. 둘은 서로 독립이라 하나만 써도 된다.

## 3장. Path A - 관측자를 백엔드에 심기 (제일 먼저 할 일)

### 3-1. 왜 이것부터인가

이 경로의 결정적 장점: **firmware를 한 줄도 안 고쳐도 된다.** 관측자는
창고에 명령을 내리지 않는다(지우기도, 옮기기도 없음). "이 조각은 계산 안
해도 된다"고 판단해 NPU 호출을 건너뛸 뿐이다. 무효화가 필요하면 새 데이터로
**덮어쓰면** 된다. 지우개가 필요 없는 설계다.

### 3-2. 관측자는 무엇을 보고 판단하는가

조각이 도착하면 두 정보가 있다: 토큰들 자체와 그 토큰들의 **절대 위치**
(문장에서 몇 번째인가). 관측자는 노트(mirror)에 지금까지 본 토큰을 위치별로
적어두고, 새 조각이 오면 비교한다:

- 위치가 이어짐 (지난 조각 끝 = 이번 조각 시작) -> **CONTINUATION** (진행 중)
- 위치가 0인데 노트에는 내용이 있음 -> **NEW_TURN** (새 턴! 프롬프트를
  처음부터 다시 보내는 중 - 재사용 기회)
- 위치가 뒤로 감 -> **REWIND** (위층이 뭔가 잘라냈음)
- 위치가 노트 범위를 건너뜀 -> **GAP** (있어선 안 되는 구멍 - 안전장치
  발동, 구멍을 -1로 메워 절대 재사용되지 않게 함)

NEW_TURN이 오면 조각의 토큰들을 노트와 대조한다. **완전히 일치하면 창고에
이미 그 구간의 K/V가 있다는 뜻이므로 NPU 호출을 생략한다.** 중간부터 다르면
다른 지점부터 계산하고 노트를 덮어쓴다.

### 3-3. `wants_output` - 가장 힘줘서 경고하는 부분

예외가 하나 있다. 프롬프트가 **완전히** 캐시에 있어도 **마지막 조각만은
반드시 계산**해야 한다. 사용자는 "다음 토큰"을 원하고, 다음 토큰을 뽑으려면
마지막 조각의 최종 출력(logits, 각 단어의 확률표)이 필요한데, K/V는 캐시에
있어도 logits는 저장해 두지 않았기 때문이다.

"이 조각이 logits를 내야 하는 조각인가"를 알려주는 플래그가 `wants_output`
이다. 두 가지 설정 실수:

- 항상 true -> 모든 조각이 "출력 필요"가 되어 **아무것도 생략 못 함**
  (모듈이 무용지물)
- 항상 false -> 마지막 조각까지 생략해 **답이 안 나옴** (정확성 파괴)

정답은 llama.cpp가 조각마다 표시해 주는 출력 행 개수(n_outputs)를 연결하는
것이다.

### 3-4. F1~F4 - firmware에게 요구하는 4가지 약속

"안 고쳐도 된다"의 전제는 firmware가 이미 이렇게 동작한다는 것이다:

- **F1 (기억을 지우지 마라)**: 새 턴이 시작돼도(위치 0이 다시 와도) 창고를
  자동으로 비우면 안 된다. 비우는 firmware라면 그 동작부터 꺼야 한다.
- **F2 (지정한 자리에 넣어라)**: "위치 3,000번에 이 토큰의 K/V를 넣어라"
  하면 정확히 그 자리에, 이미 뭐가 있으면 덮어쓰며 넣어야 한다. 같은 것을
  두 번 넣어도 결과가 같아야 한다(멱등성) - 이 성질 덕에 "애매하면 다시
  계산"이 항상 안전해진다.
- **F3 (인과적 attention)**: 위치 p의 토큰을 계산할 때 p **이하** 위치의
  K/V만 참조해야 한다(표준 동작). 이게 지켜지면 창고 뒤쪽에 남은 옛 턴의
  찌꺼기 데이터는 절대 참조되지 않으므로 지울 필요가 없다. "지우개 없는
  설계"가 안전한 수학적 이유다.
- **F4 (중간부터 시작, 선택)**: 조각 중간에서 분기가 발견되면 그 지점부터만
  계산하면 이상적인데, NPU 커널이 임의 시작 위치(RoPE 위치 오프셋)를
  지원해야 한다. 지원 안 되면 **조각 전체를 다시 계산해도 된다**(F2의
  멱등성 덕에 결과 동일, 약간 느릴 뿐). 하드웨어 검증 전에는 전체 재계산으로
  시작하라.

## 4장. Path B - 계획자를 host에 심기

### 4-1. 계획자의 하루

```
1. 턴 시작: 응용이 프롬프트 전체를 들고 plan_prefill(prompt) 호출
2. 계획자: 장부와 대조 -> "8,000토큰 일치. 단, 창고를 8,000 이후로 잘라야
   함(이전 턴 찌꺼기 제거)" -> kv_trim 명령 + 새 토큰의 조각 계획 반환
3. 응용: 조각들을 NPU 드라이버에 제출 (제출할 때마다 장부에 "보냈음" 기록)
4. 드라이버: 완료 보고가 올 때마다 장부에 "확정됨" 기록
5. 생성 단계: 토큰이 하나 나올 때마다 append_decoded로 장부에 추가
   (다음 턴에 이 답변까지 재사용하기 위해)
```

### 4-2. epoch - 이 모듈의 심장

유일하게 어려운 개념이다. 문제 상황:

> 창고를 8,000에서 자르라고 명령한 **직후**, 자르기 전에 보냈던 옛 작업의
> "완료 보고"가 뒤늦게 도착하면? 그걸 장부에 반영하면 장부와 창고가
> 어긋난다. 어긋난 장부로 다음 턴을 재사용하면 **엉뚱한 답이 조용히**
> 나온다.

해결책이 **epoch(세대 번호)**다. 창고를 변경(자르기/비우기)할 때마다 세대
번호를 올리고, 모든 작업 제출서에 현재 세대 번호를 도장 찍는다. 완료 보고는
그 도장을 그대로 들고 와야 하며, **도장의 세대가 낡았으면 보고를 버린다**.
"최적화한다고 이걸 빼지 말라"고 강조하는 이유: 이 도장이 비동기 세계에서
장부의 정확성을 지키는 유일한 울타리이기 때문이다.

실패 처리도 같은 원리다: 작업이 중간에 실패하면 창고가 어디까지 써졌는지
알 수 없으므로 마지막 확정 지점까지 창고를 자르고(동기점 복원), 세대 번호를
올려 낡은 보고를 전부 차단한 뒤 거기서부터 다시 시작한다. 데이터를 잃어도
**틀리지는 않는** 설계다.

### 4-3. Path B가 드라이버/firmware에 요구하는 것 (진짜 추가 작업)

Path A와 달리 새 명령이 필요하다: (1) `kv_trim`(위치 p부터 끝까지 무효화)
실제 커맨드, (2) 완료 보고에 epoch 되돌려주기(프로토콜에 64비트 필드 추가),
(3) 부분 실패 후 trim이 일관 상태를 복원한다는 보장, (4) 제출은 위치 구멍
없이 순서대로 온다는 가정(계획자가 보장, firmware는 assert 가능).

### 4-4. llama.cpp 안에서라면

llama-server에는 이미 "prefix 비교 후 재사용" 로직(`cache_prompt`)이 있다.
그러니 **계획 부분은 중복 구현하지 말고**, server가 "여기부터 잘라" 하고
내리는 명령(`seq_rm`)을 **진짜 창고 명령으로 번역하는 부분**(trim + epoch)만
KvLedger에서 가져다 `llama_memory_i` 구현 안에 넣으라는 것이 영문판 2.3절의
요지다. 지원 못 하는 요구(중간 구간 삭제, 상태 저장 등)는 정직하게 "불가"를
반환하면 server가 전체 재계산으로 폴백한다 - 느려질 뿐 틀리지 않는다.

## 5장. 검증 순서 - 왜 이 순서인가

1. **내 PC에서 테스트** (`cmake` 3단계 또는 POSIX `make test`): 하드웨어
   없이 논리부터. 이 테스트들이 곧 명세다.
2. **가짜 창고를 진짜 드라이버로 교체**: 단, 진짜 창고는 들여다볼 수 없으니
   "창고 내용 == 프롬프트" 검사는 불가능 -> **최종 출력(logits)을 CPU 계산
   결과와 비교**하는 것으로 대체한다. CPU가 채점 기준(golden reference)이다.
3. **F4 검증**: 조각 중간 시작이 하드웨어에서 되는지 - 일부러 어중간한
   위치(12,345)에 분기를 만들어 확인.
4. **실전 워크로드**: 에이전트처럼 매 턴 재전송하는 시나리오로 생략률과
   TTFT 개선을 실측.
5. **장기 내구 테스트**: 무작위 절단 + 주기적 실패 주입 후에도 CPU와 결과가
   같은지.

순서의 논리: **논리 -> 배관 -> 하드웨어 특이점 -> 실전 -> 내구.** 앞 단계를
건너뛰면 뒷 단계에서 문제가 터졌을 때 원인 층을 못 찾는다.

## 6장. 함정 목록 - 각각 한 문장씩

- **토큰 경계 표류**: 재사용 비교는 글자가 아니라 토큰 ID로 한다. 지난
  답변을 다시 토큰화했을 때 경계가 달라지면(채팅 템플릿 문제) 일치 길이가
  소리 없이 줄어든다 - 실제 토크나이저로 2턴짜리 테스트를 꼭 하라.
- **타임스탬프**: 프롬프트 앞부분에 매번 바뀌는 값이 있으면 재사용이 그
  지점에서 끊긴다. 뒤로 옮기거나 정규화하라. A/B 측정은 요청 페이로드를
  기록해 원본/정규화본을 재생하고 턴별 재사용률 R_t = (P_t - E_t)/P_t 로
  보고한다.
- **logits 조각은 절대 생략 금지** (3-3절).
- **노트(mirror)를 함부로 줄이지 말 것**: "일치하는 조각이 왔으니 노트를
  여기까지로 줄이자"는 그럴듯해 보이지만, 뒤 조각들이 대조할 꼬리를
  파괴하는 알려진 버그다. 그래서 진행 위치(cursor)와 유효 범위(valid_end)를
  **따로** 둔다.
- **분기 이후는 반드시 절단**: 분기점 뒤의 토큰이 우연히 같아도 attention은
  앞 문맥 전체에 의존하므로 그 K/V는 이미 오염이다. "혹시 몰라 남겨두기"
  금지.
- **새 창고 명령을 추가하면 epoch 규칙도 따라간다** (device 변이 = 세대
  번호 증가).
- **폴더 안의 ci.yml은 repo 루트에 있어야만 동작**한다.

## 7장. 마일스톤 - 한 줄 요약

M-pc1 관측자 가동(F1~F3 확인 + logits 일치) -> M-pc2 중간 시작(F4) 검증
또는 공식 보류 -> M-pc3 드라이버에 trim+epoch 추가되면 계획자 테스트를
실기로 -> M-pc4 llama.cpp 정식 통합(`llama_memory_i`)으로 server 재사용 E2E.

---

**전체를 한 문단으로**: 들여다볼 수 없는 NPU 창고를 "장부"로 원격 관리해
반복 프롬프트의 재계산을 없애는 코드이며, firmware 무수정으로 되는
관측자(모듈 2)를 먼저 켜고, 창고 명령(trim+epoch)이 준비되면 계획자(모듈 1)
를 얹는다 - 모든 단계에서 "틀리게 빠른 것"이 아니라 "안 되면 재계산으로
폴백해서 항상 맞는 것"을 원칙으로 삼는다.
